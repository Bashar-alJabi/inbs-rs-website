# INBS Real Estate — development standards

## INBS project architecture — mandatory working rules

Treat `Bashar-alJabi/inbs-website` (`main`) as the **reference for established architecture and implementation patterns**, but edit **only** `Bashar-alJabi/inbs-rs-website`. Never use the old `Bashar-alJabi/inbs-realestate` repository.

Before each implementation or refactor, inspect the corresponding working files in the original INBS website. Preserve the target project's existing structure and change only what the task requires. If a different approach is genuinely better, explain and justify it rather than silently changing conventions.

### File organization (non-negotiable)
- `src/app/[locale]/page.tsx`: thin route entry / metadata and locale validation, not a giant page component.
- `src/components/home/homepage.tsx`: page composition only. Each meaningful Home section has its own independent React component under `src/components/home/`. Use the same pattern for other pages.
- `src/content/<page>.ts`: bilingual editorial copy and page-specific data. Shared company information lives in a single shared content module; never duplicate it in JSX.
- **Exactly ONE page-specific CSS file per page:** `src/styles/home.css` for Home, `src/styles/about.css` for About, and similarly for other pages. Keep all sections' styles for that page together, organized by clear comments/headings within this one file. **Do not create one CSS file per section, component or responsive breakpoint.** Keep global tokens and genuinely shared layout styles in their already-established global/shared stylesheet(s). Reuse patterns from the original INBS site rather than inventing a new CSS layout.
- Reusable header/footer components live in `src/components/layout/`, not inside the homepage shell. When introducing globally shared chrome in the locale layout, ensure it works on every actual page; do not prematurely add empty pages.
- Preserve semantic HTML, RTL/LTR, both locales, static rendering, responsive behavior, light/dark mode, reduced-motion accessibility and focus handling.

### Engineering and review rules
- Do not create fake properties, testimonials, figures, listings, forms or claims. Use only approved real assets and grounded content.
- Never introduce an unnecessary dependency, large refactor, unrelated UI feature or architectural convention.
- Use small, coherent commits on `feature/*` branches, draft PRs to `redesign`, and merge **only after the user's explicit approval**; do not modify `main` without separately approved integration.
- Avoid Vercel deployments for feature-branch iterations. Use GitHub Actions and local development.
- Before reporting success, run or verify lint, TypeScript, production build and relevant smoke checks **against the latest commit**. Preserve existing test coverage and update it when changing real behavior.
- Compare and review the final file tree against these rules, not just whether a build passes. Do not claim a test or review ran when it did not.
